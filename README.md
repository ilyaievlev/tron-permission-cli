# tronperm — TRON Account Permissions CLI

CLI-утилита на Python для безопасного анализа, симуляции и управления правами доступа (Owner & Active Permissions, Multi-Signature) аккаунтов в блокчейне TRON.

> **Важно:** `tronperm` — это **не кошелёк**. Это специализированный инструмент аудита и конфигурирования прав доступа аккаунтов TRON. Приватные ключи используются исключительно локально для подписи транзакций и никогда не передаются по сети.

---

## Возможности

- **Инспекция прав (`permissions`):** получение актуальной структуры Owner и Active permissions, баланса TRX и человекочитаемой расшифровки разрешённых контрактов (TRX, TRC-20 / смарт-контракты, смена прав).
- **Проверка доступа (`check`):** анализ одного или группы ключей/адресов на достижимость порога (`threshold`) и возможность совершения конкретных операций.
- **Безопасная генерация ключей (`key generate`):** локальная криптографически стойкая генерация пар ключей (secp256k1) с шифрованием в Keystore (AES-256-GCM + PBKDF2).
- **Импорт существующего ключа (`key import`):** сохранение hex-ключа из TronLink / Trust Wallet в тот же зашифрованный Keystore без записи открытого текста на диск.
- **Симуляция и Dry-Run (`permission update --dry-run`):** расчет детального DIFF до отправки транзакции, проверка рисков блокировки аккаунта (lockout) и наличия средств на сетевую комиссию (100 TRX).
- **Безопасное обновление (`permission update`):** получение свежего состояния блокчейна, расчет новой конфигурации, явное текстовое подтверждение (`confirm`), подпись и верификация результата в сети.
- **Переводы TRX и USDT (`transfer trx` / `transfer usdt`):** мультиподпись одной транзакции несколькими `--key`, выбор Owner/Active `permission_id`, dry-run и проверка threshold.

## Ключевые концепции TRON Permissions

1. **Owner Permission (`id = 0`):**
   - Главное разрешение аккаунта. Имеет высшие полномочия, включая право изменять структуру любых permissions.
   - Не содержит битовой маски `operations` (разрешены любые действия).

2. **Active Permissions (`id >= 2`):**
   - Разрешения для ежедневных операций (перевод TRX, взаимодействие со смарт-контрактами TRC-20/USDT и т.д.).
   - Содержат поле `operations` — **32-байтовую (64 hex-символа) битовую маску** системных типов контрактов TRON (`ContractType`).
   - Номер бита $N$ определяет право на вызов контракта с типом $N$ (например: бит 1 = `TransferContract` / TRX, бит 31 = `TriggerSmartContract` / TRC-20).

3. **Веса и Порог (`weights` & `threshold`):**
   - Каждое разрешение содержит минимальный порог голосов (`threshold`) и список адресов подписывающих лиц с весами (`weight`).
   - Операция разрешена только в том случае, если суммарный вес предоставленных валидных подписей $\ge threshold$.

4. **Комиссия сети за обновление прав:**
   - Транзакция `AccountPermissionUpdateContract` сжигает фиксированную комиссию **100 TRX** (помимо комиссии за bandwidth). Утилита автоматически проверяет наличие необходимого баланса.

5. **Полная перезапись конфигурации:**
   - В протоколе TRON обновление прав полностью перезаписывает всю конфигурацию аккаунта. Нельзя «добавить один ключ» — необходимо передать целостную новую структуру. `tronperm` автоматически запрашивает свежее состояние и формирует корректный пакет.

## Схема работы: как устроен «второй ключ» (Multisig)

В TRON аккаунт — это не просто один кошелек с одним ключом. **Аккаунт — это учетная запись с таблицей разрешений (Permissions)** в блокчейне.

- По умолчанию аккаунтом `TAAA...` единолично управляет его создатель: Owner = `TAAA...` (вес 1), порог (`threshold`) = 1.
- **Второй ключ — это абсолютно новая, независимая пара ключей** (`Private Key B` $\rightarrow$ `Address B: TBBB...`), математически никак не связанная с первым ключом.
- Мы просим блокчейн добавить адрес `TBBB...` в таблицу доверенных лиц аккаунта `TAAA...` и меняем порог на `2` (схема 2-из-2, требуется согласие обоих) или оставляем `1` (схема 1-из-2, резервный доступ при потере основного ключа).
- **Приватный ключ `B` блокчейн никогда не видит!** Сеть хранит только публичный адрес `TBBB...`.

### Пошаговая схема

```
[Шаг 1: Локально]   Генерируем Key B -> получаем Address B (TBBB...)
       │
[Шаг 2: Локально]   Шифруем Key B паролем -> сохраняем в keys/signer-2.json (AES-256-GCM)
       │
[Шаг 3: В блокчейн] Отправляем транзакцию смены прав: добавляем адрес TBBB... с весом 1
       │            (Подписываем текущим ключом A, сжигается комиссия сети 100 TRX)
       │
[Шаг 4: Готово]     Аккаунт TAAA... теперь управляется парой: Key A + Key B
```

### 1. Откуда берётся второй ключ?
- **Через утилиту:** создаётся криптографически стойкий случайный ключ:
  ```bash
  tronperm key generate --name signer-2
  ```
- **Либо внешний ключ:** импортируйте hex из TronLink / Trust Wallet в Keystore:
  ```bash
  tronperm key import --name owner-mainnet
  ```
  Для проверки прав без подписи достаточно адреса кошелька (`--address T...`).

### 2. Где и как он хранится?
- При генерации утилита запрашивает пароль и шифрует приватный ключ алгоритмом **AES-256-GCM** с KDF **PBKDF2-HMAC-SHA256 (600 000 итераций)**.
- Файл сохраняется в `keys/signer-2.json` с правами доступа `0600` (только для владельца).
- Внутри файла открыт только публичный адрес `TBBB...`, а приватный ключ надёжно зашифрован.

### 3. Как он попадает в блокчейн?
1. Запускается симуляция (Dry-Run), чтобы увидеть точный DIFF и убедиться в отсутствии рисков блокировки:
   ```bash
   tronperm permission update --add-address TBBB... --threshold 2 --dry-run
   ```
2. Выполняется отправка в сеть:
   ```bash
   tronperm permission update --add-address TBBB... --threshold 2
   ```
3. Пользователь вводит подтверждение `confirm` и предоставляет **приватный ключ текущего владельца (A)** для подписи.
4. Транзакция `AccountPermissionUpdateContract` попадает в блокчейн, с баланса сгорает 100 TRX комиссии, и с этого момента для любых операций требуется вес $\ge 2$.

### 4. Где и как брать второй ключ потом?
- **Подпись транзакций через CLI:** при операциях, требующих подписи второго ключа, указывается файл `--key keys/signer-2.json`. Утилита спросит пароль, расшифрует приватный ключ в оперативной памяти ровно на время подписания хеша и сразу сотрёт его из памяти.
- **Проверка прав без пароля:** команда `tronperm check --key keys/signer-2.json` читает только открытый адрес из файла и сразу показывает статус в сети, не требуя ввода пароля.
- **Экспорт в сторонние кошельки:** зная пароль от файла, приватный ключ всегда можно извлечь как стандартную 64-символьную hex-строку и импортировать в любой другой софт с поддержкой Multisig TRON.

## Установка и настройка

### 1. Требования
- Python `>= 3.10`

### 2. Установка в виртуальное окружение
```bash
# Клонирование репозитория
git clone https://github.com/ilyaievlev/tron-permission-cli.git
cd tron-permission-cli

# Создание и активация виртуального окружения
python3 -m venv .venv
source .venv/bin/activate

# Установка зависимостей и CLI в режиме разработки
pip install -e .
```

### 3. Конфигурация (.env)
Скопируйте пример конфигурации:
```bash
cp .env.example .env
```

Параметры файла `.env`:
```ini
# Сеть TRON: shasta (по умолчанию для тестов), nile или mainnet
TRON_NETWORK=shasta

# API-ключ TronGrid (рекомендуется для Mainnet)
TRONGRID_API_KEY=

# Адрес аккаунта по умолчанию (чтобы не передавать его в каждой команде)
TRON_ACCOUNT=TYourTronAddressHere

# Опционально для разработки (НЕ рекомендуется для продакшена):
# OWNER_PRIVATE_KEY=
```

## Использование CLI

### 1. Просмотр текущих permissions (`permissions`)
Получает свежее состояние аккаунта из блокчейна, проверяет баланс TRX и декодирует маску операций:

```bash
# Использовать адрес из .env:
tronperm permissions

# Или указать конкретный адрес:
tronperm permissions TJRabPrwbZy45sbavfcjinPJC18kjpRTv8
```

Пример вывода:
- Таблица **OWNER** с текущим порогом и списком ключей с их весами.
- Таблицы **ACTIVE** с наглядным отображением статусов операций:
  - `Переводы TRX: YES/NO`
  - `TRC-20 / Смарт-контракты: YES/NO`
  - `Смена прав: YES/NO`

---

### 2. Проверка уровня доступа ключей (`check`)
Позволяет проверить, какой уровень доступа даёт один или группа ключей:

```bash
# Проверка по адресам:
tronperm check --address TAAA... --address TBBB...

# Проверка по зашифрованному файлу ключа (адрес извлекается без ввода пароля):
tronperm check --key keys/signer-1.json

# Комбинированная проверка:
tronperm check TAccountAddress --address TAAA... --key keys/signer-2.json
```

Утилита суммирует доступные веса и проверяет, преодолевают ли они `threshold` для Owner и каждого Active permission:
```text
OWNER (#0)
Порог (Threshold): 2
Доступный вес:     2
Доступ к Owner:    YES

ACTIVE #2 'active0'
Порог (Threshold): 2
Доступный вес:     1
Доступ к Active:   NO

  TRX transfer:    NO
  TRC-20 transfer: NO
  Permission edit: NO
```

---

### 3. Генерация нового ключа (`key generate`)
Генерирует новую пару ключей TRON и сохраняет зашифрованный Keystore:

```bash
tronperm key generate --name cold-signer
```

1. Локально генерируется пара ключей `secp256k1`.
2. В терминале запрашивается пароль шифрования (ввод скрыт).
3. Файл сохраняется в `keys/cold-signer.json` с правами доступа `0600` (`-rw-------`).

#### Генерация с мгновенной подготовкой смены прав (`--add-permission`):
```bash
tronperm key generate --name cold-2 --add-permission --type owner --weight 1 --threshold 2
```

---

### 4. Импорт существующего ключа (`key import`)
Сохраняет уже имеющийся hex-ключ (TronLink, Trust Wallet и т.п.) в зашифрованный Keystore. Приватный ключ не пишется в файл открытым текстом и не должен попадать в `.env` (`OWNER_PRIVATE_KEY` — только для тестовых сетей).

```bash
tronperm key import --name owner-mainnet
```

1. В терминале запрашивается hex приватного ключа (ввод скрыт).
2. Запрашивается пароль шифрования (дважды, ввод скрыт).
3. Из ключа вычисляется TRON-адрес — сверьте его с адресом в кошельке.
4. Файл сохраняется в `keys/owner-mainnet.json` с правами `0600`.

Если файл с таким именем уже есть, укажите другое `--name` или повторите с `--force`.

Дальше этот файл передаётся в команды подписи и проверки:

```bash
tronperm check --key keys/owner-mainnet.json
tronperm permission update --dry-run --key keys/owner-mainnet.json
```

---

### 5. Обновление permissions (`permission update`)

#### Безопасная симуляция (Dry-Run):
Перед реальным изменением конфигурации запустите симуляцию:
```bash
tronperm permission update --add-address TNewSignerAddress... --threshold 2 --dry-run
```
Утилита:
- Построит proposed-структуру;
- Покажет подробную таблицу **DIFF** (добавленные, удаленные, измененные ключи);
- Проверит баланс аккаунта на наличие 100 TRX;
- Предупредит о риске потери контроля над аккаунтом (lockout);
- Не отправит ни одного байта в сеть.

#### Выполнение обновления прав:
```bash
tronperm permission update --add-address TNewSignerAddress... --threshold 2
```
Процесс выполнения:
1. Выводится предупреждение о сети (для `MAINNET` — ярко-красный баннер).
2. Выводится детальный **DIFF**.
3. Запрашивается явное подтверждение: `confirm`.
4. Запрашивается ключ текущего владельца для подписи (hex либо расшифровка указанного `--key keys/owner.json`).
5. Транзакция собирается, подписывается и отправляется в сеть.
6. Утилита дожидается включения транзакции в блок и повторно запрашивает обновлённое состояние для контроля.

Для схемы 2-of-2 передайте оба keystore:

```bash
tronperm permission update --add-address TCCC... --threshold 2 \
  --key keys/owner-shasta.json \
  --key keys/signer-2.json
```

### 6. Перевод TRX и USDT с мультиподписью (`transfer`)

Деньги всегда уходят **с аккаунта** (например `TVsHK...`), а не с адреса второго ключа. Ключи только подписывают транзакцию.

Перед отправкой CLI:
- читает актуальные permissions;
- выбирает Owner (`permission_id = 0`) или Active (`id >= 2`);
- проверяет, что сумма весов подписей ≥ `threshold`;
- для Active дополнительно проверяет битовую маску операций (`TransferContract` для TRX, `TriggerSmartContract` для USDT);
- показывает план и требует `confirm`.

#### Симуляция перевода TRX

```bash
tronperm transfer trx TRecipientAddress... --amount 1.5 \
  --from TVsHKrCVHWNa6pY5h8dVVSxL2S9KnxrhXx \
  --key keys/owner-shasta.json \
  --key keys/signer-2.json \
  --dry-run
```

#### Реальный перевод TRX (2-of-2 Owner)

```bash
tronperm transfer trx TRecipientAddress... --amount 1.5 \
  --from TVsHKrCVHWNa6pY5h8dVVSxL2S9KnxrhXx \
  --key keys/owner-shasta.json \
  --key keys/signer-2.json \
  --permission-id 0
```

После `confirm` утилита отдельно спросит пароль каждого keystore, подпишет одной транзакцией оба ключа и отправит её в сеть.

#### Перевод USDT (TRC-20)

```bash
tronperm transfer usdt TRecipientAddress... --amount 10 \
  --from TVsHKrCVHWNa6pY5h8dVVSxL2S9KnxrhXx \
  --key keys/owner-shasta.json \
  --key keys/signer-2.json
```

Контракт USDT выбирается по сети:

| Сеть | Контракт USDT |
|---|---|
| mainnet | `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t` |
| shasta | `TG3XXyExBkPp9nzdajDZsozEu4BkaSJozs` |
| nile | `TXYZopYRdj2D9XRtbG411XZZ3kM5VkAeBf` |

Его можно переопределить `--contract` или `USDT_CONTRACT` в `.env`.

#### Как CLI выбирает permission

- Если указан `--permission-id`, используется он (0 = Owner, 2+ = Active).
- Если не указан, берётся permission, которое **разрешает операцию** и **набирает threshold** переданными ключами. Предпочтение у того, куда входят все указанные ключи.
- Важно: если второй ключ добавлен **только в Owner**, Active может по-прежнему быть 1-of-1. Тогда перевод одним ключом через Active всё ещё возможен. Для принудительного 2-of-2 укажите `--permission-id 0` или ужесточите Active.

## Безопасность

- **Защита ключей:** приватные ключи шифруются по стандарту **AES-256-GCM** с формированием ключа через **PBKDF2-HMAC-SHA256** (600 000 итераций, криптографическая соль 16 байт).
- **Права доступа:** файлы в `keys/` создаются с маской `0o600` (чтение и запись только владельцу файла).
- **Изоляция:** директория `keys/*` и файл `.env` находятся в `.gitignore`.
- **Защита от утечек:** класс `GeneratedKey` скрывает приватный ключ в `repr`, исключая его попадание в трейсбеки и консольные логи.
- **Защита Mainnet:** выделение опасных операций предупреждающими баннерами при работе с основной сетью.
